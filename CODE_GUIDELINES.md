# Code Guidelines

Rules for all code in this repository, written by a human or generated by an AI agent.
Language-agnostic. Conventions that are specific to a programming language live in `docs/conventions/<language>.md`, not here; the convention for which *human* language to write in is `docs/conventions/taal.md`.

## How to read this file

- Every rule is **Must** (blocking; a reviewer rejects the change) unless marked **Prefer** (the default; deviating is fine if the reason is written in the PR description).
- This file is guidance, not enforcement. Anything that has to hold 100% of the time (formatting, linting, type checks, secret scanning, tests) belongs in a pre-commit hook or CI pipeline. Once tooling enforces a rule, delete it here.
- Every rule added weakens the others, for humans and agents alike. Keep this file under 250 lines.

---

## 0. If you read nothing else

1. Read the surrounding code first. Match the patterns that are already there.
2. Search the repo before writing anything new. Extend what exists instead of adding a second version.
3. Build the smallest thing that solves the actual problem. Nothing speculative.
4. Errors are handled or propagated. Never swallowed.
5. Validate everything that crosses a trust boundary.
6. No secrets, credentials or real customer data in the repository. Ever.
7. Ambiguous requirement? Ask. Do not guess and build.
8. Ship complete code, end to end: callers, tests and docs updated. No stubs, no placeholders.

---

## 1. Before writing code

If any answer is a guess, stop and ask. A five-minute question beats a two-day rewrite.

- What problem is being solved, for whom, and what does "done" look like concretely?
- Does something in this codebase already do this, or half of it?
- Edge cases: empty, null, zero, one, many, huge, malformed, concurrent, slow, offline.
- What happens when this fails?

Assumptions go in the PR description or the response, never silently into the code.

---

## 2. Structure and naming

- One unit (function, class, module) has one responsibility. If the name needs "and", split it.
- Respect layer boundaries. Presentation calls business logic, business logic calls data access. Never the other way around, never skipping a layer. No business rules in controllers, views, handlers or templates.
- No I/O (database, network, filesystem, clock, randomness) inside pure logic. Inject it so it can be tested.
- Directory layout mirrors the domain, not the framework's tutorial.
- Delete unused variables, dead branches, commented-out code and orphan files. Version control remembers.
- Name magic numbers and literal strings.

| Naming rule | Good | Bad |
|---|---|---|
| Intent over mechanics | `expiredSubscriptions` | `filteredList2` |
| No unexplained abbreviations | `maxRetryCount` | `mxRtCnt` |
| Booleans read as a question | `isActive`, `hasAccess` | `flag`, `check` |
| Functions start with a verb | `calculateInvoiceTotal` | `invoiceStuff` |
| One casing per language, repo-wide | `userId` everywhere | mixing `userId` and `user_id` |

---

## 3. Simplicity and size

**Prefer.** Soft limits; crossing one is a signal to split, not a failure.

| Metric | Target | Split above |
|---|---|---|
| Function length | under 50 lines | 80 |
| Nesting depth | 3 | 4 |
| Parameters | 4 (object/struct beyond that) | 6 |
| Cyclomatic complexity | under 10 | 15 |
| File length | under 300 lines | 500 |

- Guard clauses and early returns over `if` pyramids.
- Boring, readable code beats clever one-liners. Every time.
- Rule of three: duplicate twice, abstract on the third occurrence, with the real requirements visible. No abstraction for a single caller.
- No configuration options, hooks, plugin layers, generic frameworks or forwarding-only wrappers that nothing currently uses.

---

## 4. Errors and failure

- Catch an exception only when there is something useful to do: handle it, add context, or translate it to the layer's own error type. Otherwise let it propagate. An empty catch block is a bug with a hiding place.
- Fail fast on programmer errors (invalid state, broken invariants). Fail gracefully on expected conditions (network down, invalid input).
- On failure, deny by default. No silent fallback to a default value when a lookup or check fails.
- User-facing error messages say what went wrong and what to do next. Never stack traces, queries, file paths or internal identifiers.
- Log with context (operation, identifiers, state) and a severity that means something. Never log secrets, tokens or personal data.
- Release resources deterministically with the language's scoped construct (`defer`, `with`, `using`, `try-with-resources`).
- Every external call has a timeout. Retries use backoff and a maximum attempt count, and only for idempotent operations.

---

## 5. Duplication and reuse

- One authoritative implementation per piece of knowledge: one place validates an email, one place formats currency, one place knows the tax rate.
- Copy-pasted blocks that diverge later are the most common source of long-lived bugs in this codebase. Every future change then carries the obligation to find and evaluate every sibling.
- Refactoring a shared helper is part of the task, not a separate ticket.

---

## 6. Security

Trust nothing that comes from outside the process, including other internal services. Security review is part of every code review, not a separate gate.

- Validate at the boundary, server-side, always. Check type, length, range and format before the value reaches business logic. Allow-lists over deny-lists.
- Encode on output for the target context (HTML, SQL, shell, URL, log, JSON) at the point of use.
- Never build queries or commands with string concatenation. Parameterised queries and prepared statements only. Shell arguments as a list, never a formatted string.
- Secrets come from environment variables or a secrets manager. Never hardcoded, committed, logged or put in error messages. Rotate anything that leaks.
- Passwords are hashed with argon2id, bcrypt or scrypt through the platform's standard library. No custom crypto, no custom auth, no custom session handling.
- Authorise every request at the point of data access, not only in the UI. Ask "does this specific user own this specific record", not "is this user logged in".
- Least privilege for database users, API tokens, service accounts, file permissions and container capabilities.
- **Prefer** returning 404 over 403 when revealing that a resource exists is itself a leak.
- All transport is TLS. No exceptions for internal traffic.
- Collect the minimum personal data, delete it when the purpose ends, keep production data out of development and test.
- Dependencies: pin versions, review before adding, run a vulnerability scan in CI. Patch critical and high findings within 7 days, the rest within 90.

---

## 7. Data and performance

- Correct first, then measure, then optimise. Optimising without a measurement is guessing.
- Never query inside a loop. Batch, join or preload.
- Every list endpoint and every query that can grow is paginated or bounded. No unbounded `SELECT *`.
- Index what you filter, sort and join on.
- Schema changes go through versioned migrations. A migration is reversible or ships with a documented rollback. Never edit a migration that has already been merged.
- Slow work (email, PDF generation, chained third-party calls) runs asynchronously in a queue, job or worker, never inside a request handler.
- **Prefer** streaming large payloads over loading them fully into memory.
- Cache only when you know the key, the TTL and the invalidation rule. A cache without an invalidation story is a future bug.
- Know the complexity of what you write. O(n²) over a growing collection is a production incident on a timer.

---

## 8. Interfaces and APIs

- Contract first. Plural nouns for resources, no verbs in paths (`/users/5`, not `/getUser?id=5`).
- One casing across the entire API surface. Never mix.
- Status codes: 200 read/update, 201 create, 204 delete, 400 invalid input, 401 unauthenticated, 403 unauthorised, 404 not found, 409 conflict, 422 semantic validation, 429 rate limited, 500 unexpected.
- One stable error shape across the whole API: machine-readable code, human-readable message, field-level details where relevant.
- Breaking changes need a version, a deprecation period and a migration note.
- Public endpoints, functions and modules are documented where they are defined (OpenAPI, docstrings, type signatures), generated from the code where possible.

---

## 9. Testing

- New behaviour ships with tests. Bug fixes ship with a test that fails without the fix.
- Test behaviour through the public interface, not private internals. Tests that assert implementation details break on every refactor and teach the team to ignore them.
- Cover the edge cases from section 1, not just the happy path.
- Tests are deterministic: no real clock, no real network, no random ordering, no dependency between test cases.
- Integration tests run against a real test database. Mock only what you do not own and cannot run locally.
- A test that only asserts that a mock was called proves nothing. Delete it.
- Never change an assertion, skip a test, or loosen a lint or type rule to make CI green. If the test was wrong, fix it and say so in the PR.
- Coverage is a signal, not a goal. 100% on trivial getters means nothing; one untested payment path means everything.

---

## 10. Version control and review

- One concern per commit, one purpose per PR. Refactoring and behaviour change never travel together; the reviewer cannot see the risky part through the noise.
- Commit messages explain why. The diff already shows what.
- Never commit generated files, local config, `.env`, credentials or large binaries.
- Every PR is reviewed by someone other than the author. No merge without approval.
- A PR description states: what changed, why, how it was tested, what could break.
- Reviewers check, in this order: does it do the right thing, does it break something else, is it safe, is it maintainable, does it follow this file. Spotting a security concern and approving anyway is negligence, not politeness.

---

## 11. Comments and documentation

- Comment the why: the trade-off, the constraint, the reason this looks strange. If a comment is needed to explain what the code does, rewrite the code.
- No commented-out code, no changelog comments, no `// updated by X on Y`. That is what git is for.
- `TODO` requires a ticket reference or it does not get merged.
- Public modules and non-obvious algorithms get a short docstring: purpose, inputs, outputs, failure modes.
- Update the README when setup, commands or architecture change. Stale documentation is worse than none.

---

## 12. Extra rules for AI agents

Everything above applies. These exist because generated code fails in specific, repeatable ways: duplication instead of reuse, errors hidden instead of fixed, invented APIs, and green CI achieved by weakening the checks.

- Verify that every library, function, method and configuration key exists in the version this project depends on. Do not invent API surface.
- Run the tests, linter and type checker before claiming they pass, and report the actual output. Never write "tests should pass".
- Change only what the task requires. No opportunistic reformatting, renaming or "while I was in there" refactors. Do not delete or rewrite working code outside the scope of the request.
- Deliver runnable, complete code. No `...`, no `// implement the rest`, no functions that return a hardcoded example value.
- Do not add a dependency for something the standard library or an existing dependency already does.
- Do not generate defensive null checks, validation layers or abstraction layers that nothing asked for.
- Do not add comments that restate the line below them. No emoji, banners or ASCII art in code, logs or CLI output unless the project already does it.
- Put code in the existing file that is the right place. Create a new file only when no such file exists.
- A stated doubt is worth more than a confident guess. If the correct answer is "this cannot be done cleanly with the current structure", say that instead of producing something that technically runs.

---

## 13. Definition of done

A change is done when every line is true:

- [ ] It solves the stated problem, including the edge cases.
- [ ] It reuses what existed instead of duplicating it.
- [ ] Names, structure and style match the surrounding code.
- [ ] Errors are handled or propagated with context, never swallowed.
- [ ] Input from outside is validated; output is encoded; no secrets in the diff.
- [ ] Meaningful tests exist and pass locally. Linter, formatter, type checker and security scan pass with zero warnings.
- [ ] The diff contains nothing unrelated to the task.
- [ ] Callers, tests and documentation are consistent with the change.
- [ ] You would show this change to a new team member on day one as the example to follow.

## Project specifics

```
Stack:            Elixir 1.17 / Phoenix 1.7 / Ecto (control_plane), Go 1.26 (agent),
                  Next.js 16 / React 18 / TypeScript (frontend), PostgreSQL 16.

Run locally:      There is no local toolchain. Everything runs in containers on the
                  platform VM. Author here, sync, run there.

Run tests:        bash tools/check.sh            (format, compile, credo, deps.audit,
                                                  mix test, gofmt, vet, go test)
                  bash tools/check.sh elixir|go  (one component)
                  Tests run against a throwaway Postgres (bf-test-pg, tmpfs) that
                  tools/check.sh starts itself; never against production.

Lint / format:    Included in tools/check.sh. CI additionally runs Dialyzer,
                  staticcheck, govulncheck, npm audit, tsc and eslint, gitleaks over the full
                  history, and every migration rolled back and re-applied.

Build:            bash build-prod.sh && bash deploy-prod.sh        (control plane)
                  bash deploy-frontend.sh                          (frontend + edge)
                  The worker binary is built into the CP image and served at
                  /dist/bunk-worker; nodes curl it from there.

Architecture:     One control plane, many resource nodes. The control plane owns all
                  state and decisions; each node runs a Go agent that only ever dials
                  OUT over HTTPS — enrol, heartbeat, poll for commands, dial back for
                  a console. Nothing reaches into a node, which is what lets a node
                  live behind NAT on someone else's connection. Real docs:
                  docs/architecture.md, docs/design/multi-node.md, docs/protocol.md,
                  docs/runbooks/.

Known oddities:   - `:ssh.connect/3` with an already-connected socket does not complete
                    on OTP 27. The console relay listens on loopback for that reason
                    and no other.
                  - `mix deps.audit` and Hex's own retirement data disagree. Both run;
                    each has found advisories the other missed.
                  - There is no `POST /nodes/{node}/qmrestore` in the Proxmox API.
                    A restore is the guest-create endpoint with an `archive` param.
                  - `CommandController.result_attrs/1` is an allow-list. A command kind
                    that reports a new field must be added there too, or the control
                    plane records the result and silently drops the payload.
                  - systemd parses `OnFailure` only in `[Unit]`. In `[Service]` it logs
                    "Unknown key" and the alarm is wired to nothing.
                  - The `.html.eex` mail templates are a pixel port of the previous
                    platform's branding. Do not restyle them casually.

Do not touch:     .env.prod and every backup of it (secrets, gitignored, never commit).
                  Migrations that are already merged — add a new one instead.
                  frontend/src/components/ui/ (shadcn-generated primitives).
```
